# Slot 94 dies after a Reset because someone records a state block — the runtime restores its own method pointers, and `Present`/`Reset` are not in the set it restores

Filed by: `/gr`, 2026-09-04
Topic: `external-research/topics/2026-09-04-a-recorded-state-block-rewrites-the-device-vtable-and-kills-an-in-place-patch.md`
Dossier section: §9a (the post-Reset disarm) and the board's `[PD]` row *"WHY DOES A DEVICE RESET DISARM THE STEREO?"*

- **The dossier's prime suspect — UE3 re-creating the device onto an unpatched vtable — does not fit.** D3D9 vtables are shared per runtime class, a second `CreateDevice` would have logged, and `Present` (slot 17, same table) kept firing. Only slot 94 was rewritten. `[inferred-static 2026-09-04]`
- **Two independent public witnesses name the rewriter: `IDirect3DDevice9::BeginStateBlock`/`EndStateBlock`.** gho (DxWnd, 2014): *"BeginStateBlock recover all COM method pointers invalidating the hook patching. It's sufficient to hook this method to restore back the DxWnd routines."* Paul Roussin (D3D8 newsgroup): *"BeginStateblock will reset the device table so you have to … reset your modified addresses."* Recording mode swaps the state-setting methods and restores the runtime's originals afterwards; `Present`/`Reset` are not state-setting, so they survive — exactly the observed pattern. `[reported]` → `[hypothesis]` for this game until instrumented.
- **UE3's own D3D9 RHI records no state blocks** (public source mirror, one code search), so the caller is another resident — Steam overlay, driver overlay, anything on `ID3DXSprite`/`ID3DXFont` — re-initialising after the reset. `[inferred-static 2026-09-04]`
- **⚠️ The "not instantaneous" clue is weaker than §9a states:** the stereo summary counts "since last summary" over a `g_frameInterval` window, so one healthy post-reset summary is expected even if the hook died at `Reset` itself. Re-measure with a per-frame stamp before keeping the 120–240-frame figure.
- **Discriminating instrumentation, all `[PD]`:** (1) in `My_Present`, compare `vtbl[94]` to `&My_SetVSConstF`, log the frame and the new value on first mismatch — equal to `orig_SetVSConstF` means the runtime restored it; (2) hook slots 60/61 (`BeginStateBlock`/`EndStateBlock`) to log frame + caller module. (3) Durable fix, cheapest first: re-apply the patches after every `EndStateBlock` (DxWnd's fix); or code-hook `orig_SetVSConstF` with MinHook (immune to table rewrites); or wrap the device (overkill for one slot).

Suggested dossier change: in §9a, replace "Prime suspect: UE3 re-creating its RHI/device objects onto a vtable the patch no longer covers" with the state-block mechanism as the leading `[hypothesis]`, the reason the old suspect is excluded, and the three-line instrumentation above as the `[PD]` row's content. Mark the "runs ~120–240 frames after `Reset`" figure as needing a per-frame re-measure.
